# Document AI — multi-workspace RAG assistant

Upload documents into a workspace, ask questions grounded in them (with citations), and let the assistant take actions through tools. Every workspace shares **one** vector table, and isolation is enforced inside the vector query.

## Features
- Email/password login (Supabase Auth), multiple workspaces per user, workspace switcher.
- Upload `.pdf`, `.txt`, `.md` (max 4 MB). Ingestion: parse → chunk (per page, ~1000 chars, 150 overlap) → embed (Gemini, 768 dims) → store in the shared `document_chunks` table. Re-uploading the same file adds nothing (content hash).
- RAG chat: retrieval via the `match_chunks` SQL function (`WHERE workspace_id = …` inside the vector search), answers cite `[n]` sources; honest "I don't know".
- Tools (model proposes, server validates with zod `.strict()` and runs): `save_task`, `list_tasks`, `send_summary` (Discord webhook). Every call is logged, including rejected ones.
- Dashboard: documents, chat history, tool-call log, tasks, and a "Show retrieval" debug view (workspace, chunks, similarity, latency, tokens).

## Run locally
```bash
npm install
cp .env.example .env.local   # fill in values, see below
# Supabase SQL Editor: run supabase/schema.sql
npm run dev                  # http://localhost:3000
npx playwright install chromium && npm run test:e2e   # optional end-to-end tests
```

## Environment variables
| Name | Where from | Exposure |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase → Project Settings → API | public |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase publishable key (`sb_publishable_…`) | public (RLS protects data) |
| `GEMINI_API_KEY` | Google AI Studio | **server only** |
| `GEMINI_CHAT_MODEL` | a model that passes a real `generateContent` call | server |
| `GEMINI_FALLBACK_MODELS` | comma-separated fallbacks, tried on 429/503/404 | server |
| `GEMINI_EMBED_MODEL` | `gemini-embedding-001` (768 dims) | server |
| `DISCORD_WEBHOOK_URL` | Discord channel → Integrations → Webhooks | **server only** |

Supabase setup: enable the `vector` extension, turn **off** "Confirm email", run `supabase/schema.sql`.

## Isolation (defense in depth)
1. Routes take `workspaceId` from the URL and call `requireMember()`; it is never read from the body or from the model.
2. `match_chunks` filters by `workspace_id` inside the vector query.
3. Row-level security on all tables (membership-based).

## How I worked with AI
Full write-up: [AI_NOTES.md](AI_NOTES.md). Context files used exactly as in the repo: [CLAUDE.md](CLAUDE.md) (project rules the AI had to follow), [AGENTS.md](AGENTS.md) (generated by Next.js; tells the AI to read the bundled Next 16 docs before coding) and [PROJECT_GUIDE.md](PROJECT_GUIDE.md) (the step-by-step plan I worked from).

**Tool and split.** Claude Code did most of the typing: scaffold, SQL, API routes, UI, tests. I set the requirements and the isolation rules in `CLAUDE.md`, created the Supabase/Gemini accounts and keys myself, and checked results in the browser. The plan was written first and followed phase by phase (auth → workspaces → ingestion → chat/RAG → tools), with a check after each phase.

**How I kept the AI honest**
- *Rules up front:* `CLAUDE.md` states the non-negotiables (workspace filter inside the SQL query, `workspace_id` never from the model, secrets server-only, zod `.strict()` on tool args, document text is data not instructions).
- *Docs over memory:* before using Gemini and PDF libraries, the AI read the installed type definitions instead of guessing method names; for Next 16 it read the bundled docs, which showed `middleware.ts` had become `proxy.ts`.
- *Prove it, don't trust it:* Playwright end-to-end tests (`e2e/`) run the quality bar against the real app and database: create/switch workspaces, a second user blocked, duplicate upload, PDF ingestion, grounded answer with citation, honest "I don't know", Toyota cannot see Ferrari's secret, the injected document triggers no tool, `save_task` really writes a row, unknown tools/bad arguments are rejected.

**Where the AI went wrong and what caught it** (details in AI_NOTES.md)
1. Its `match_chunks` SQL failed in Supabase (`operator does not exist: extensions.vector <=> extensions.vector`): `vector` lives in the `extensions` schema, so `search_path` needed `public, extensions`. Caught by the SQL editor error; fixed in `supabase/schema.sql`.
2. It picked `gemini-2.5-flash`, which is listed by the API but returns 404 for new accounts. Caught by the first end-to-end chat test (empty answer, error in the server log). Fixed by testing real `generateContent` calls and adding a fallback model chain.
3. It logged tool calls only after the whole answer succeeded, so an LLM failure after `save_task` would leave a side effect with no log. Found while reviewing the failure path; now each call is logged the moment it runs.
4. Debugging detour that was my tooling, not the app: a zsh quirk (`$m:generateContent`) produced fake 404s for every model.

**Decisions that were mine** _(fill in / confirm in your own words before submitting)_: local-first practice run before deploying; Supabase pgvector in one shared table; Gemini free tier; Discord webhook for the notification tool.

**What I would improve:** hybrid search with the same workspace filter on both branches, streaming responses, async ingestion queue, cross-workspace sharing (opt-in).

## Known limitations
- Free-tier Gemini: ~5 requests/minute per model; the app falls back to other models and shows a rate-limit message when all are exhausted.
- `send_summary` needs `DISCORD_WEBHOOK_URL`; without it the call is logged as an error and the assistant says so.
- No streaming; scanned (image-only) PDFs have no text to extract.
